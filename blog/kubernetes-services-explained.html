Kubernetes Services Explained: Why They Exist and the Problem They Solve

Understand how Kubernetes Services provide a stable endpoint, enable load balancing, and keep applications reliable even as Pods come and go.

By Keshav Site Reliability Engineer · Kubernetes notes

One of the first questions many engineers ask when learning Kubernetes is:

Why do we need a Service when we already have Pods?

The answer becomes clear once you understand one important fact:

Pods are temporary, but applications need a permanent way to communicate.

Let's see why.

The Problem: Pods Are Ephemeral

Imagine you deploy a simple web application.

Initially, Kubernetes creates one pod:

web-abc123
IP: 10.244.1.5

Another application, such as a user service, communicates with it using:

http://10.244.1.5:8080

Everything works perfectly.

Now imagine the pod crashes. Kubernetes immediately creates a replacement pod:

web-xyz789
IP: 10.244.2.18

The original pod no longer exists, and its IP address is gone forever. The user application is still trying to reach:

10.244.1.5

Since that address no longer exists, communication fails. This is the problem Kubernetes Services are designed to solve.

The core problem

Applications need a stable way to communicate, but Pods are dynamic and their IP addresses keep changing.

The Solution: Kubernetes Service

Instead of communicating directly with a pod, applications communicate with a Service.

User Pod
    │
    ▼
Web Service
IP: 10.106.187.51
    │
    ▼
web-abc123

If the pod crashes, Kubernetes creates another one.

User Pod
    │
    ▼
Web Service
IP: 10.106.187.51
    │
    ▼
web-xyz789

Notice what changed:

  • The pod changed.
  • The pod IP changed.

Notice what didn't change:

  • The Service IP.
  • The Service name.

Applications continue working without any configuration changes.

✓ The Service IP and name stay stable. Only the Pods behind the Service change.

How Does a Service Know Which Pod to Use?

Services don't hardcode pod names. Instead, they use labels.

A Deployment may create pods with the following label:

labels:
  app: web

The Service selects pods using the same label:

selector:
  app: web

Kubernetes constantly watches the cluster. Whenever a pod appears with:

app=web

it is automatically added to the Service. Whenever that pod disappears, Kubernetes automatically removes it. No manual intervention is required.

What Happens During Scaling?

Suppose the Horizontal Pod Autoscaler (HPA) increases the number of replicas. Instead of one pod, you now have:

web-1
web-2
web-3

The Service automatically discovers all of them.

              Service
                 │
        ┌────────┼────────┐
        ▼        ▼        ▼
      web-1    web-2    web-3

Every incoming request is distributed among the available healthy pods.

Applications never need to know:

  • How many pods exist
  • Which pod is serving the request
  • What each pod's IP address is

The Service handles all of that automatically.

The Four Major Problems a Service Solves

Without a Service:

  • Pod IP addresses constantly change.
  • Applications lose connectivity when pods restart.
  • Clients must know individual pod addresses.
  • Scaling becomes extremely difficult.

With a Service:

  • A stable virtual IP address.
  • A stable DNS name.
  • Automatic load balancing.
  • Automatic discovery of healthy pods.

This allows applications to communicate reliably even though the underlying pods are constantly being created, deleted, and replaced.

Real-World Example: Robot Shop

Consider the Robot Shop application. The browser doesn't communicate directly with the web pod. Instead, it communicates with the web Service.

Initially:

Browser
   │
   ▼
Web Service
   │
   ▼
web-56ff6c54c-m7n6f

Later, HPA increases the replicas:

Browser
   │
   ▼
Web Service
   │
   ├── web-56ff6c54c-m7n6f
   ├── web-84f5c89b7-abcde
   └── web-6d8f7b9c4-xyz12

The browser still connects to the same Service. The Service distributes requests across all available pods. The client never notices that the application has scaled.

An Easy Analogy

Imagine calling a company.

You don't know which employee will answer your call. You simply dial the company's main phone number. The receptionist answers and forwards your call to an available employee.

If one employee goes home and another starts their shift, you continue calling the same company number. The receptionist always knows who's available.

In Kubernetes:

  • Pods are the employees.
  • The Service is the receptionist.
  • The Service IP or DNS name is the company's phone number.

Applications don't need to know where individual pods are running. They simply communicate with the Service, and Kubernetes handles the rest.

Key Takeaways

A Kubernetes Service is much more than a networking object. It provides a stable identity for an application while hiding the dynamic nature of pods behind the scenes.

Without Services, every pod restart or scaling event would require applications to rediscover new IP addresses, making reliable communication nearly impossible.

By introducing a stable endpoint, automatic pod discovery, and built-in load balancing, Kubernetes Services enable applications to remain available and resilient, even as the underlying infrastructure constantly changes.

Understanding Services is one of the biggest milestones in learning Kubernetes because almost every production application depends on them.
