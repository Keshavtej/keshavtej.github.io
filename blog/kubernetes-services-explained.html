Kubernetes Services Explained: Why They Exist and the Problem They Solve

Understand how Kubernetes Services provide stable endpoints, route traffic, and keep applications connected even as Pods come and go.

8 min read Beginner friendly Networking
By Keshav Site Reliability Engineer · Kubernetes notes

One of the first questions many engineers ask when learning Kubernetes is:

Why do we need a Service when we already have Pods?

The answer becomes clear once you understand one important fact:

Pods are temporary, but applications need a stable way to communicate.

Let's see why.

The Problem: Pods Are Ephemeral

Imagine you deploy a simple web application.

Initially, a Deployment creates one Pod:

web-abc123
IP: 10.244.1.5

Another application, such as a user service, communicates with it using:

http://10.244.1.5:8080

Everything works perfectly.

Now imagine the Pod crashes. Its Deployment creates a replacement Pod:

web-xyz789
IP: 10.244.2.18

The original Pod no longer exists, and its IP address no longer points to that workload. The user application is still trying to reach:

10.244.1.5

Since that address no longer exists, communication fails. This is the problem Kubernetes Services are designed to solve.

The core problem

Applications need a stable way to communicate, but Pods are dynamic and their IP addresses keep changing.

The Solution: Kubernetes Service

Instead of communicating directly with a Pod, applications communicate with a Service. This example uses the default Service type, ClusterIP.

User Pod
    │
    ▼
Web Service
IP: 10.106.187.51
    │
    ▼
web-abc123

If the Pod crashes, its Deployment creates another one.

User Pod
    │
    ▼
Web Service
IP: 10.106.187.51
    │
    ▼
web-xyz789

Notice what changed:

  • The Pod changed.
  • The Pod IP changed.

Notice what didn't change:

  • The Service IP.
  • The Service name.

Clients continue using the same Service endpoint without changing their configuration.

✓ The Service IP and name stay stable. Only the Pods behind the Service change.

How Does a Service Know Which Pod to Use?

Services don't hardcode Pod names. Instead, a Service usually uses a selector that matches Pod labels.

A Deployment may create Pods with the following label:

labels:
  app: web

The Service selects Pods using the same label:

selector:
  app: web

The Kubernetes control plane watches for Pods with:

app=web

It then updates the Service's EndpointSlices as matching Pods appear, disappear, or change readiness. This keeps the set of available backends current without manual updates.

What Happens During Scaling?

Suppose the Horizontal Pod Autoscaler (HPA) increases the workload's desired replica count in response to its configured metrics. Instead of one Pod, you now have:

web-1
web-2
web-3

The control plane adds the matching, ready Pods to the Service's EndpointSlices.

              Service
                 │
        ┌────────┼────────┐
        ▼        ▼        ▼
      web-1    web-2    web-3

New connections are routed to available, ready endpoints. The exact traffic distribution depends on the cluster's Service implementation and configuration.

Applications never need to know:

  • How many Pods exist
  • Which Pod is serving the request
  • What each Pod's IP address is

The Service abstraction keeps those details out of the client configuration.

The Four Major Problems a Service Solves

Without a Service:

  • Pod IP addresses can change when Pods are replaced.
  • Applications can lose connectivity when Pods restart.
  • Clients must track individual Pod addresses.
  • Scaling becomes extremely difficult.

With a Service:

  • A stable virtual IP address for a standard ClusterIP Service.
  • A stable DNS name.
  • Traffic routing across available endpoints.
  • Automatic tracking of matching, ready Pods.

This allows applications to stay connected even as the underlying Pods are created, deleted, and replaced.

Real-World Example: Robot Shop

Consider the Robot Shop application. The browser doesn't communicate directly with a web Pod. External traffic typically enters through an Ingress, Gateway, or load balancer and then reaches the web Service.

Initially:

Ingress / Load Balancer
   │
   ▼
Web Service
   │
   ▼
web-56ff6c54c-m7n6f

Later, HPA increases the replicas:

Ingress / Load Balancer
   │
   ▼
Web Service
   │
   ├── web-56ff6c54c-m7n6f
   ├── web-84f5c89b7-abcde
   └── web-6d8f7b9c4-xyz12

The external entry point still targets the same Service, which routes new connections to its available endpoints. The client does not need to track how the application has scaled.

An Easy Analogy

Imagine calling a company.

You don't know which employee will answer your call. You simply dial the company's main phone number. The receptionist answers and forwards your call to an available employee.

If one employee goes home and another starts their shift, you continue calling the same company number. The receptionist always knows who's available.

In Kubernetes:

  • Pods are the employees.
  • The Service is the receptionist.
  • The Service IP or DNS name is the company's phone number.

Applications don't need to know where individual Pods are running. They communicate with the Service endpoint, and the cluster routes traffic to an available backend.

Key Takeaways

A Kubernetes Service is a networking abstraction that provides a stable identity for an application while hiding the dynamic set of Pods behind it.

Without Services or another discovery mechanism, clients would need to rediscover backend IP addresses after Pod replacement or scaling events.

By providing stable discovery and automatically maintained endpoints, Kubernetes Services help applications stay connected as the underlying workloads change.

Understanding Services is one of the biggest milestones in learning Kubernetes because almost every production application depends on them.
